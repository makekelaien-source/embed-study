## 理想混控与履带标定

约定车体前进为正，俯视逆时针为正角速度；每条履带的正速度都表示带动车体前进。左右电机因镜像安装产生的接线极性，在驱动适配层分别标定，不改变这个上层约定。

理想无滑移模型中，令车体线速度为 `v`（m/s）、偏航角速度为 `ω`（rad/s）、有效履带间距为 `b_eff`（m）：

$$
v_L=v-\frac{\omega b_{\mathrm{eff}}}{2},\qquad
v_R=v+\frac{\omega b_{\mathrm{eff}}}{2}
$$

两侧同速同向为直行；两侧反向同速为理想原地转向。实际履带转向包含侧向滑移和地面摩擦，几何中心距不能直接保证实际转角。`b_eff` 是待标定的简化模型参数，需分别记录桌面材质、履带张紧、载荷、速度和转向方向；换表面或载荷后重新检查。Gazebo 的履带控制器也分别提供履带间距和转向效率参数，说明二者应分开建模；本项目不照抄其默认效率。[Gazebo TrackedVehicle 官方接口](https://gazebosim.org/api/sim/8/classgz_1_1sim_1_1systems_1_1TrackedVehicle.html)

地面围挡内，在已有停止保护的条件下，用独立角度观测验证低速转弯。近似稳定片段中可由 `(v_R-v_L)/ω_measured` 估计有效间距；编码器记录的是传动运动，并不直接测得履带相对桌面的滑移。角速度接近零或观测不稳定的片段不用于反推。这个标量模型不足以证明任意转弯轨迹。

履带线速度也不直接等于电机轴转速或 PWM。驱动轮、减速比、编码器安装轴确定后，再建立每米计数/转速换算。无编码器时只能先做限时、低速的开环台架试验，不宣称距离或转角精确。

若一侧目标速度超限，两侧必须乘同一个比例：

$$
s=\min\left(1,\frac{v_{\max}}{\max(|v_L|,|v_R|)}\right),\qquad
(v_L',v_R')=s(v_L,v_R)
$$

双侧均为零时取 `s=1`。共同缩放保留理想速度比；分别裁剪会改变理想曲率。它不限制加速度，也不计算实际停车距离。

### 当前固定动作协议与数学模型的关系

当前动作协议的业务字段为 `command_id`、`action`、`speed_mm_s` 和 `duration_ms`。会话、消息序号与时效校验按总通信契约处理；不要另造与其冲突的消息格式。`command_id` 标识本次请求，`duration_ms` 是有上限的请求持续时间，最终仍受本地许可和停止条件约束。

`speed_mm_s` 表示**每条履带目标线速度的幅值**，单位 mm/s，不是车体中心速度，也不是实测履带速度。令 `s=speed_mm_s/1000`，符号约定如下：

| `action` | 左履带目标（m/s） | 右履带目标（m/s） | 含义 |
|---|---:|---:|---|
| `FORWARD` | `+s` | `+s` | 理想前进 |
| `REVERSE` | `-s` | `-s` | 理想后退 |
| `LEFT` | `-s` | `+s` | 左右履带反转的逆时针原地转向 |
| `RIGHT` | `+s` | `-s` | 左右履带反转的顺时针原地转向 |
| `STOP` | 停止目标 | 停止目标 | 由独立高优先级停止路径处理 |

`LEFT/RIGHT` 的理想车体中心平移速度为零，不能把 `speed_mm_s` 当作转弯时的车体前进速度。真实速度、旋转中心和偏航率仍需编码器、控制器及底盘标定证明。未来连续 `v/ω` 请求可作为扩展设计；当前协议没有 `TWIST` 动作，本节公式不会自动新增线上命令。

## SBC 提建议，ESP32 决定能否运动

香橙派负责视觉采集、已限定的动作请求和状态展示；ESP32 在本地控制周期内独立检查保护条件。LLM 的文字输出不能直接改 PWM、使能脚或任意串口命令。屏幕只读取状态，刷新、DMA 等待、语音合成或模型卡住都不能阻塞安全任务。

ESP32 固件待实现的受理顺序：

1. 上电、复位、欠压、看门狗复位和初始化期间，驱动使能由明确的硬件状态保持关闭，目标速度为零。
2. 检查实体停机、驱动故障、电流/电源条件和本地传感器；任一失效先进入停止状态。
3. 验证当前连接会话、单调递增命令序号、接收本地时间与动作时效。旧会话、重复、乱序、积压动作一律拒绝。
4. 分别检查通信心跳与**本动作方向的安全许可**。心跳只证明链路活着，不能延长旧视觉帧、方向许可或旧动作的寿命。
5. 将允许的目标转为左右履带速度，统一限幅，再经经过验证的加速与换向过程交给驱动适配层。每个周期仍检查停止条件。
6. 期限届满或保护触发时撤销当前目标、清空待执行动作并关闭/制动。恢复传感器或释放实体开关后仍保持零输出，等待新的有效请求，不自动续跑。

会话号、序号、动作 TTL、方向许可 TTL 与心跳都以 ESP32 的本地单调时钟判定。SBC 若发送“剩余有效期”，须先扣除采集帧龄和经测量的最坏传输余量；ESP32 只能接受到达时仍有正余量的许可。具体毫秒数由最坏响应与停车距离决定，本文不提供可直接启用的阈值。

`local_inputs` 是本地采样快照，其采样时刻、有效截止时间和传感器结果只能由本地采样链路更新。**主控心跳不能延长快照的截止时间**，不能把旧快照重新包装成新读数，也不能让过期或缺失的方向感知恢复有效。参数示例仅用于配置和故障回放，不是已经测得的采样周期、许可时限或停止能力。

硬件看门狗用于检测固件失去正常执行，运动输出的目标失效状态仍是 **OFF**。须验证卡死、复位及启动期间的实际电平；不能把“启用了看门狗”当作已经实现电机断能。乐鑫说明 IWDT/TWDT 的检测对象与动作由配置决定。[ESP32-S3 看门狗文档](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/system/wdts.html)

线上 ACK 的状态枚举固定如下，并带请求标识、原因及 `physical_verified`：

| ACK 状态 | 契约含义 |
|---|---|
| `accepted` | 请求已受理，尚不代表已应用输出或完成运动 |
| `rejected` | 请求未获受理，保留拒绝原因 |
| `output_applied` | 适配层已确认应用输出；不能据此证明履带已经转动或达到目标速度 |
| `completed` | 真实硬件后端确认动作完成，必须携带`physical_verified=true`与相应证据；只能陈述已验证的速度/停车等范围，不能据此推断位移或角度 |
| `aborted` | 请求因停止、保护等原因提前结束 |
| `failed` | 请求处理或适配执行失败 |
| `simulated_stopped` | 模拟器已进入停止状态，不代表真实电机已经停住 |

`physical_verified` 用来明确这条结果是否具有实物验证证据。`accepted`和`output_applied`不自动置真；线上`completed`只允许为真，否则协议拒绝。纯软件计时/控制窗口结束只能报`simulated_stopped`且保持为假，不能报`completed`。`running`、`stopped`、`fault`可用于本地状态或遥测，**不是线上ACK枚举**。收到请求不等于动作完成；语音回执依据实际ACK及其验证范围生成。第一版不让LLM自由规划轨迹。

## 每个方向单独建立保护覆盖

| 动作 | 至少要核验的空间 | 当前不能据此推断的能力 |
|---|---|---|
| 前进 | 左右履带最先失去承托的位置、前角与车头外伸部位、直向和斜向边缘 | 前置相机“前方清晰”不代表整个车体安全 |
| 后退 | 两条履带后端、尾部与后角，以及后向停止余量 | 前向图像与前部 ToF 不能签发后退许可 |
| 原地转向 | 前后左右车角、两条履带外缘和车体整体扫掠区域 | 前后各一只 ToF 不自动覆盖侧向扫掠 |
| 行进转弯/倒车转弯 | 当前速度组合下的外侧角、内外履带路径、外壳悬伸与停止过程 | 直行验收不能替代转弯验收；实际旋转中心可能偏移 |

以**实际可能运动的完整外廓和承托区域**建立覆盖图，并考虑加速/减速与换向过程。触及未知区域的动作禁用，先调整传感器位置或增加相应方向感知。单目视觉的桌纹、阴影、反光、低纹理或透明表面仍可能造成错误判断，必须保留独立本地测距与无效读数停止。

现有 [forward_guard.c](../forward_guard.c) 只实现前进方向的会话、视觉许可和限时联锁。其 `permitted` 输入也依赖调用层提供真实的 ToF、心跳与实体停机状态。它没有实现后退、原地转向、轨迹扫掠、驱动故障、电流检测或接线，不能把返回值用于全部动作。后续需新建并独立测试方向感知的保护接口。

可用的提前量应大于“该方向最坏接近速度 × 最坏检测/许可失效/控制响应时间 + 最差停车距离 + 余量”。正反转、斜向和转弯逐项实测，正常制动与切断驱动后的滑行分别测。履带没有离开桌面不等于整机外壳和重心仍安全。[既有视觉与联锁台架说明](../vision-face-runbook.md)

## 驱动、电源和控制器接入

驱动选型从实际电机与载荷出发：核对工作电压范围（包括电池满充和回生瞬态）、每路持续电流、启动/堵转电流、峰值允许时长、限流、故障输出和在机壳内的散热。左右履带同时启动、卡滞与转向摩擦都要计入。载板散热和端子能力不能用芯片宣传峰值替代。先使用带可控限流的台架电源；不要求学生长时间锁死电机测堵转，优先取得厂商数据，再制定受控测量方案。[Pololu 电压、电源与电机电流选型说明](https://www.pololu.com/docs/0J84/3.1)

驱动适配层先根据真实数据手册确定 `enable / direction / pwm / brake / coast / fault` 契约，再确定 GPIO。若集成 H 桥已经处理内部开关互锁，按其输入真值表和切换要求工作；若器件需要外部互补 PWM，必须核对死区与电气安全状态。MOSFET 的死区不能代替机械换向停顿。ESP32 MCPWM 提供死区和故障制动能力，但需要正确配置并核验输出电平，本框架尚未配置这些外设。[ESP32-S3 MCPWM 文档](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/peripherals/mcpwm.html)

一般动作变更先按已验证的加速度斜坡降至零，再确认满足停转/电流释放条件，才切换方向并缓慢起步。斜坡期间左右速度比可能变化，保护范围须覆盖实际输出。实体停机或危险触发不能为了舒适斜坡延后停止，须立即进入经验证的驱动安全状态。制动、滑行与断能的结果按实物测量，不能假定输出为零就立即静止。

编码器到位后，先核对左右方向、计数丢失、采样周期与每米计数，再分别建立左右速度环。PID 需要输出限幅、积分抗饱和、零速/停机时清积分及编码器失效处理；参数由架空和地面低速试验取得。没有编码器的当前草案不包含可启用 PID 参数。

电池采用与电机及稳压支路匹配的成品方案。BMS、主保险/限流、线材与端子、可靠的电机支路实体停机、充电器/USB-C 充电管理和电池化学体系/串数一起确认。BMS 不替代合适的充电器与支路保护；USB-C 插座也不证明支持所需充电电压或边充边用。首次接线、极性确认与通电测量由用户在场完成，未确认方案前不提供带电操作或采购完成的记录。

| 顺序 | 工作 | 升级到下一步前的证据 |

| 4. 联合负载 | 摄像头持续采集、语音推理/播报、屏幕刷新、履带启动并发；复现相机/串口/屏幕故障 | 停机链路不被阻塞，电压/温度/最坏延迟合格，语音与运动各自记录结果 |
| 5. 合盖与电池 | 实物固定、散热、线束防磨与电池/充电复核，重新测故障停止与温升 | 合盖、材质/载荷变化后的真实结果完整；仍未知的方向保持禁用 |

上述顺序是待执行计划。桌面移动必须在对应方向保护、供电和地面试验通过后进行；无人时仅允许软件回放和已授权的静止诊断，不自行启动实物履带。

## 可运行的纯数学支架

[motion_math.py](motion_math.py) 只计算带符号的左右履带线速度与共同限幅比例，不导入 GPIO/串口库、不连接硬件，也不实现许可、PID、加速、换向或看门狗。正值、有限值与必填几何均会校验，`None`、`pending`、零值、非有限值等不能作为已确认配置。

在 `05-projects/desktop-robot` 目录运行：

```powershell
.\.venv\Scripts\python.exe -m unittest framework.test_motion_math
.\.venv\Scripts\python.exe framework/motion_math.py --linear 0.20 --angular 1 --track-gauge 0.18 --effective-gauge 0.20 --max-track-speed 0.15
```

以上所有数值都是**数学测试样例**，不是设备尺寸、已标定速度或允许行驶设置。该例原始目标为左 `0.10 m/s`、右 `0.30 m/s`，共同缩放为 `0.5` 后输出左 `0.05 m/s`、右 `0.15 m/s`。不能从这个 JSON 推断实物确实以该速度运动或运动是安全的。

测试涵盖单位线速度/角速度、停止、倒车、左右原地转向、倒车转弯、共同饱和保比、物理/有效间距分离以及未知/非有限配置拒绝。实际运行结果以执行日志为准，本文不把数学测试记为实车验收。

2026-11-12 已实际执行上述单元测试：**8 项通过**；示例命令输出左约 `0.05 m/s`、右 `0.15 m/s`、比例约 `0.5`，`hardware_action=false`；两个 Python 文件的 `py_compile` 通过。未连接或驱动任何电机。
